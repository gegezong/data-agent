# DataAgent 目标产品设计

## 1. 产品定位

DataAgent 的目标不是“让用户用自然语言查一张表”，而是一个面向销售经营管理的 **分析型 Agent（Sales Operations Analysis Copilot）**。它把管理者的一句业务问题转化为可追踪的分析计划，调用多个受控分析工具取证，验证数字和假设，最后给出带证据、带口径、可继续追问的经营结论。

当前版本的 `query_sales` 已经能够证明 Pi Agent、工具调用、SQLite 和 SSE 可以连起来，但如果产品长期停留在“问题 → 一个过滤条件 → 一张结果表”，直接写查询接口就足够了。目标产品必须让 Agent 参与到 **问题拆解、工具选择、证据组织、假设验证和后续行动** 中，而不是只做 SQL 的自然语言入口。

目标闭环是：

```text
业务问题
  → 识别指标和时间范围
  → 生成分析计划
  → 多工具取数、对比、拆解、异常检测
  → 验证口径、数字一致性和数据权限
  → 结论 + 证据 + 不确定性
  → 行动建议和可继续追问的分析上下文
```

## 2. 目标用户和核心场景

### 2.1 销售负责人：解释结果变化

用户问：“华东地区本月销售额环比下降 12%，主要原因是什么？下周应该优先做什么？”

系统不应只返回华东的明细，而应：

1. 解析“本月”和对比周期，确认销售额口径；
2. 计算本月与上月的销售额、订单数和客单价；
3. 按产品、销售人员、客户行业拆解下降贡献；
4. 检测异常客户或异常产品，形成候选原因；
5. 用第二个工具验证候选原因是否能解释整体变化；
6. 按影响金额和可执行性给出行动建议，并列出依据。

### 2.2 区域经理：定位经营机会

用户问：“华东哪些产品有增长，但库存或销售覆盖不足？”

Agent 应组合销售增长、产品结构和覆盖率工具，标识机会产品，给出需要补充的数据或后续动作。若当前数据源没有库存字段，系统应明确说明缺口，不编造库存结论。

### 2.3 财务或经营分析师：复核口径

用户问：“销售额和毛利的定义是什么？这份结论使用了哪些数据？”

系统需要展示指标定义、计算公式、筛选条件、数据时间范围、权限范围、来源记录和计算版本，使结论可以复核，而不是只给一段看似合理的文字。

### 2.4 一线销售：获得个人行动线索

用户问：“我负责的客户里，过去 30 天订单金额下降最多的是哪些？应该先联系谁？”

Agent 在权限允许的范围内提供客户分层、变化原因和优先级。涉及客户联系方式、合同等敏感字段时，需要由权限策略决定是否展示。

## 3. 用户最终看到的产品形态

目标形态是“聊天入口 + 分析工作区”，而不是纯聊天窗口。

### 3.1 分析工作区

- **结论区**：展示核心指标、变化方向、影响金额和一句话结论；
- **分析计划区**：显示 Agent 将问题拆成了哪些步骤，每一步调用了什么工具、当前状态是什么；
- **证据区**：展示用于支撑结论的表格、趋势图、分组贡献图和筛选条件；
- **口径和权限区**：展示指标定义、数据更新时间、用户可见范围和可能的限制；
- **建议区**：给出按优先级排序的下一步动作，并说明建议依据；
- **追问区**：提供“继续按产品拆解”“只看华东大客户”“保存为周报”等上下文操作。

### 3.2 标准回答结构

每次分析都尽量按照以下结构返回：

1. **结论**：直接回答用户问题，给出数字和变化方向；
2. **数据证据**：列出关键期间、指标值、贡献最大的维度和来源；
3. **原因分析**：区分已验证事实、待验证假设和当前数据无法回答的部分；
4. **行动建议**：给出影响范围、优先级和建议动作；
5. **口径与限制**：说明指标定义、权限范围、数据新鲜度和样本不足等情况；
6. **继续分析**：给出可以直接点击的后续问题。

### 3.3 表格和可读性原则

表格由前端渲染组件负责列宽、数字格式和对齐，模型只输出结构化行列数据和字段语义。金额、数量、百分比、日期分别采用固定格式；移动端或窄窗口使用横向滚动和重点列固定，避免依赖 Markdown 空格对齐。

## 4. Agent 的核心价值边界

### 4.1 Agent 负责什么

- 理解业务问题、时间表达和上下文；
- 识别指标、维度、筛选条件和比较关系；
- 选择分析流程和工具组合；
- 根据中间结果决定是否继续拆解或验证；
- 组织证据、解释不确定性和生成建议；
- 保留会话上下文，让用户可以逐层追问。

### 4.2 程序和工具负责什么

- 指标计算、聚合、同比/环比、贡献度和异常检测；
- SQL 参数绑定、数据范围和权限过滤；
- 数值一致性校验、来源记录和审计；
- 超时、重试、调用次数和 Token 预算控制。

模型不直接执行任意 SQL，不凭空计算业务数字，也不绕过数据权限。Agent 的价值来自推理和编排，可信度来自确定性工具和验证器。

## 5. 目标能力分层

### P0：可演示的分析型 Agent

- 指标目录和统一指标口径；
- 单指标查询、期间比较、维度拆解、异常检测四类确定性工具；
- 结构化分析计划和受限的多步执行；
- 每个结论关联证据、筛选条件和计算 ID；
- 基于角色和数据范围的权限控制；
- SSE 推送计划、工具状态、证据和文本增量；
- Golden Questions 评测集和基础运行指标。

### P1：可供团队使用的分析产品

- 保存分析、生成周报、分享只读链接；
- 趋势图、贡献度图和可下载明细；
- 定时指标监控和异常提醒；
- 用户反馈、结论修正和提示词版本管理；
- PostgreSQL/数据仓库适配、Redis 会话和后台任务。

### P2：经营决策平台

- 多数据源联邦查询和数据血缘；
- 目标/预测/实际对比；
- What-if 模拟和预算场景分析；
- 结合用户订阅的主动洞察；
- 与 CRM、工单或任务系统的受控写入，需要二次确认和完整审计。

## 6. 目标工具箱

所有工具都使用结构化输入和结构化输出。工具是业务能力边界，也是权限和审计的边界。

| 工具 | 作用 | 典型输出 |
| --- | --- | --- |
| `search_metric_catalog` | 查找指标定义、别名和可用维度 | 指标公式、粒度、版本、负责人 |
| `query_metric` | 查询某个指标在筛选条件下的值 | 数值、单位、期间、数据范围 |
| `compare_periods` | 计算同比、环比或自定义期间差异 | 当前值、对比值、绝对变化、变化率 |
| `breakdown_metric` | 按区域、产品、人员或客户分解指标 | 分组值、贡献额、贡献率、排名 |
| `detect_anomalies` | 识别偏离基线的时间点或实体 | 异常分数、基线、影响范围 |
| `validate_hypothesis` | 验证某个候选原因是否能解释变化 | 支持/不支持、证据、覆盖率 |
| `get_evidence` | 获取可展示的明细、来源和计算记录 | 行列数据、来源、过滤器、计算 ID |
| `save_analysis` | 保存分析快照或生成报告 | 分析 ID、版本、分享策略 |

第一阶段可以继续使用 CSV 导入 SQLite。目标产品仍然建议把数据落到数据库：Agent 需要稳定的指标查询、权限过滤、索引、计算记录和可复核快照；CSV 适合作为种子数据和导入格式，不适合作为最终查询层。

## 7. 数据与指标产品设计

核心数据分为四类：

- 销售事实：订单日期、区域、产品、销售人员、客户、数量、销售额、成本和毛利；
- 维度字典：区域层级、产品层级、人员组织和客户分层；
- 指标定义：名称、公式、默认粒度、可用维度、数据负责人、版本和更新时间；
- 分析资产：分析请求、执行计划、工具结果、证据、最终回答和用户反馈。

指标定义必须可查询。例如“销售额”要明确是含税还是不含税、按订单日期还是发货日期、是否包含取消订单。Agent 先通过指标目录获取口径，工具再按定义查询，避免不同回答使用不同公式。

## 8. 权限、可信度和产品边界

- 权限在服务端和查询层强制执行，提示词中的“只看华东”不能作为安全边界；
- 结论必须引用实际工具结果，无法取证时输出“无法确认”；
- 对小样本、数据延迟、缺失字段和口径冲突明确提示；
- 外部写操作默认关闭，生成任务或发送通知必须经过用户确认；
- 分析结果记录用户、时间、指标版本、过滤条件和工具调用，支持审计。

## 9. 产品成功指标

产品不能只看模型回答是否流畅，还要看分析是否可复核：

- 事实准确率：关键数字与确定性查询结果一致；
- 权限准确率：无越权字段、无越权数据范围；
- 计划成功率：问题能选择正确的指标和工具流程；
- 证据覆盖率：结论中的数字都有可追溯证据；
- 根因有效率：专家认为主要原因具有足够解释力；
- 追问闭环率：用户可以基于同一分析上下文继续下钻；
- P95 响应延迟、工具失败率、平均工具调用次数和 Token 成本；
- 用户采纳率：保存报告、点击建议、导出结果或继续追问的比例。

## 10. 迭代路线

### 阶段一：基础工程

保留当前 Pi Agent + SQLite + SSE 的可运行骨架，补齐指标表、分析上下文、权限中间件、工具注册和事件协议。

### 阶段二：分析型 Agent

实现结构化 Planner、确定性分析工具、Verifier 和结构化回答；用 20～50 个真实业务问题建立评测集。

### 阶段三：分析工作区

把计划、证据、图表、口径和追问做成可交互界面，支持保存和分享分析。

### 阶段四：生产化

替换或并行接入 PostgreSQL/数据仓库，引入 Redis、后台任务、定时监控、日志指标和发布流程。

## 11. 面试中的项目表达

可以把项目概括为：

> 我基于 Pi Agent 二次开发了一个销售经营分析 Copilot。系统没有让大模型直接生成任意 SQL，而是通过指标语义层和受控工具完成查询、期间对比、维度拆解、异常检测和假设验证；Agent 负责生成分析计划、编排工具、组织证据和解释结果，服务端负责权限、数值校验、预算和审计。前端通过 SSE 展示计划和证据链，让分析过程可追踪、可复核、可继续下钻。

这比“用自然语言查 CSV”更能体现 Agent 应用开发、数据产品设计和工程治理能力。
